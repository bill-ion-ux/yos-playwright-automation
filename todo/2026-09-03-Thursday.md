## Tomorrow — the benchmark

### Two independent questions

1. **Authoring cost** — wall-clock time (plus token / $ cost where a tool is
   involved) to go from a fixed requirement to a script that passes green,
   for each method:
   - **M1 — WebdriverIO, hand-authored.** The current process, no AI.
   - **M2 — Playwright + `playwright-cli` + Claude.** Today's method.
   - **M3 — `playwright codegen`.** Record-and-replay, then hand-fix to green.
2. **Execution cost** — wall-clock run time of the *same finished scenario*,
   Playwright vs WebdriverIO, headless, same machine.

Keep them separate: M1–M3 answers "how fast do we write it", question 2
answers "how fast does it run once written".

### Fix ONE common scenario first

Use the **device + plan prepaid purchase** journey. It is the only flow with
both a real WDIO source (`legacy-scripts/YOS_Device_Plan.js`) and a Playwright
implementation (`tests/specs/YOS-ARS-47.spec.ts`). Broadband has no WDIO
source, so it cannot be used for the framework comparison.

Write `docs/benchmark/scenario.md` (half a page) before touching a browser:
same product, same mock-data strategy, same start state (site root), same end
assertion (`/thankyou` + order-number regex). All four scripts must target the
exact same steps.

### Method — authoring (M1, M2, M3)

For each method, starting from the frozen scenario doc:

- Stopwatch from "begin" to "passes green on a clean run" (`retries: 0`,
  headless, twice in a row).
- Record: active authoring time, number of debug / re-run cycles, and —
  M2: Claude token count + rough $ from the session;
  M3: split between record time and hand-fix time.
- Same author for all three, same day, to remove skill variance.
- Keep artifacts under `benchmark/wdio/`, `benchmark/pw-claude/`,
  `benchmark/pw-codegen/`.

Caveats to carry into the write-up:
- M3 codegen output has no assertions, no `toHaveURL` sync points, no popup
  handling, no fixture / eKYC stub — the hand-fix time **is** the real cost
  and must be counted, not just the recording.
- M2 cost includes one-off `playwright-cli` exploration of the flow; a second
  spec in the same area is cheaper once a POM exists. Measure a first spec and
  note this.
- M1's author already knows this flow (it is their script) while M2/M3
  rediscover it — either have M1 done by someone who has not seen the flow, or
  note the bias explicitly.

### Method — execution (Playwright vs WebdriverIO)

- Same machine, headless, nothing else running, wired network if possible.
- Config parity: same timeouts, same viewport; **turn `screenshot` /`trace`
  off** for the timed runs (IO skews the number). Restore after.
- **Warm up**: one throwaway run to clear the Azure cold start, then measure.
- Run each script **N = 10**, `retries: 0`. Record per-run wall time
  (Playwright: reporter duration; WDIO: spec duration).
- Report **median + min/max**, and the **count of infra failures** (FPX
  gateway never starts, cold-start timeout). Exclude infra failures from the
  timing set but report the rate — it is a real reliability signal.
- If payment-gateway noise dominates, also time a **deterministic sub-segment**
  (site root -> `/payment`, stop before Pay Now) so the framework delta is not
  drowned by backend flakiness.
